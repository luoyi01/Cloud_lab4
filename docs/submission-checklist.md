# 云原生实验验收与提交清单

本清单将课程文档的“六、提交要求”“七、评分标准”和累计不超过 10 分的加分项映射到具体交付和验证证据。本清单对应已运行的工程和真实实验记录。最终提交状态以末尾验收记录为准；评分由教师按课程标准判定，本项目不自行宣称获得分数。

## 六 提交要求

### 文件组织

课程要求的主目录与本项目的交付约定如下。

| 材料 | 内容设计 | 提交前验收 |
| --- | --- | --- |
| `src/` | API、页面、数据模型、输入校验、实例接口、依赖清单与锁定版本 | 从源码构建，业务可运行，不是空壳示例 |
| `docker/` | API/Web Dockerfile、Compose、代理配置、运行配置示例 | 镜像独立构建，端口、环境变量、通信和数据卷已验证 |
| `k8s/` | Kind 配置、Deployment、Service、ConfigMap、Secret 示例及生成方式、StatefulSet/PVC、选定的进阶资源和指标组件配置 | YAML 完整，资源 Ready，配置注入与固定入口可用 |
| `screenshots/` | 按容器化、K8s、伸缩、自愈、持久化、消融、加分实验分类 | 每张图有关键命令/输出，报告中有图号、图题与解释 |
| `report.docx` 或 `report.pdf` | 八部分报告，架构图、对比数据、真实问题和个人心得 | 独立打开，图表清楚，与原始数据及提交版本一致 |
| `README.md` | 从 clone 到部署、验证、复现实验、清理的完整步骤 | 从全新克隆目录独立复现，不需要未提交文件 |
| `scripts/` 与 `results/` | 可重复执行的验证/采样脚本、用于报告的原始数据及必要日志 | 参数、统计口径和失败结果明确，保留相关材料 |

压缩包按 `学号_姓名_云原生实验.zip` 命名。两周内完成，实际截止时间以课程群通知为准。报告与工程可分别提交或合并打包，保证教师能够独立打开与查阅。提交仓库地址作为复现入口，并在报告中记录对应的提交 SHA 或版本。

- [x] 给出 Kind 创建、镜像导入、YAML 应用、Ready 等待和访问步骤。

- [x] 每条验证说明期望现象、失败判据、结果位置和必要排查入口。
- [x] 写明清理方式与数据保留边界，避免复现者误删留言数据。
- [x] 从全新 clone 的目录完成一次验收，并记录对应提交与工具版本。

README 已通过独立克隆部署验收，记录见 results/reproduction/；指标和故障实验在主集群实测，未实施功能明确标注。

### Git 与压缩包的内容边界

Git 保存课程交付需要的工程、文档、截图和精选实验数据。`findings.md`、`progress.md`、`task_plan.md`、本地方案草稿、缓存、真实凭证、数据目录、临时渲染文件和镜像归档不进入提交。

`.gitignore` 只影响 Git 的文件选择。课程 ZIP 由 scripts/package.py 按提交目录白名单从已提交 HEAD 导出；本地未提交的报告修改不进入 ZIP。个人填写版需在最终个人提交包中自行替换。不能将 Git 公开版与本地填写版混淆，不能直接把整个工作目录压缩。ZIP 中不包含 `.git/`、本地工作记录、真实凭证或依赖缓存；配套脚本、截图和报告必须齐全。

- [x] `git status` 与 staged diff 中只有本阶段需要的文件。
- [x] README、配置和脚本引用的项目文件都在仓库中，或有明确生成步骤。
- [x] 完成相应功能验证，再提交并 push 到现有仓库。
- [x] 报告记录的提交 SHA 对应所展示的源码、镜像和配置。
- [x] 最终 ZIP 解压后，报告可直接打开，工程可按 README 复现。

## 七 评分标准 百分制

以下分值来自课程文档，总计 100 分；“设计”和“证据”是本项目落实方式。

| 评分项 | 分值 | 设计细节 | 验证与交付证据 |
| --- | ---: | --- | --- |
| 应用设计与实现 | 25 | 留言发布/查询/分页、输入校验、共享数据、原子计数、实例身份；页面展示操作结果；三单元职责清楚 | 正常业务、空输入/超长输入处理、并发计数、多副本数据一致性；源码说明与架构图 |
| 容器化 | 10 | 独立 Dockerfile、锁定依赖、Compose 网络、环境配置、命名卷、健康检查 | 从源码构建成功；端口访问、组件通信、配置修改、Redis 重启后数据验证 |
| K8s 部署与编排 | 15 | Deployment、Service、ConfigMap、Secret、探针和资源预算；Redis StatefulSet/PVC | Nodes/Pods Ready、Service 可达、配置注入、PVC Bound；提交完整 YAML |
| 弹性伸缩与自愈 | 10 | API 1→3→5→3，持续请求期间删除 API Pod，多副本与优雅终止 | desired/Ready 数量、CPU/内存、旧新 UID、事件、恢复耗时、请求成功率和错误数 |
| 消融对比实验 | 15 | 同一镜像/数据/负载，A Compose 与 B Kind 分时测量；说明现有 WSL2 基础和范围 | 启动、资源、副本管理、发现、恢复、复杂度的原始数据；至少 5 次重复与统计；如实说明跨平台范围 |
| 报告结构与规范性 | 10 | 八部分完整，图表编号、图题、截图命令清楚，引用资料可追溯 | 截图索引、验证项对应关系、图表与数据一致，Word/PDF 打开和阅读检查 |
| 心得体会与技能收获 | 15 | 以真实现象解释虚拟化/容器/编排边界、工具取舍、失败和调整 | 与实验事件对应的个人判断；保留真实疑问与改进想法，根据真实实验现象整理；公开报告身份占位，本地填写信息保留，提交前可自行调整表述 |

基础分优先顺序：先让真实业务和两条部署路径可运行，再完成强制验证，最后整理可比数据和个人分析。复杂工具数量不能替代真实证据。

报告八部分分别为：实验概述、环境与工具、应用设计与实现、部署过程记录、消融对比实验、问题与分析、心得体会与技能收获、参考文献与资料。

## 加分项 累计不超过 10 分

文档没有给每个加分项单独分值，不能按工具数量自行估算加分。所有加分内容在报告中注明实际完成状态和证据位置。

| 文档加分项 | 本项目选择 | 细节与有效证据 |
| --- | --- | --- |
| Redis Sentinel / MySQL 主从自动故障转移 | 未实施 | 真正配置主从与故障转移，注入主节点故障并记录客户端重连、恢复和数据边界；单实例 Redis 重建不能替代该项 |
| PodDisruptionBudget、StatefulSet、Ingress 等进阶资源 | 已验证 StatefulSet/PVC 与 PDB | Redis StatefulSet 的身份/PVC 与重建后数据；API PDB `minAvailable: 2` 配合 3 副本，在受控自愿驱逐实验中展示约束与替换过程 |
| 完整 CI/CD 自动部署流水线 | 未实施 | 若选择，需贯通提交→检查/构建→部署→健康验证；只做 CI 检查或镜像构建不写成完整 CI/CD |
| 多节点 K8s 集群验证节点级高可用 | 已做 API worker 停止与恢复验证 | 1 control-plane + 2 worker；API 跨 worker 分布，失效 worker 只承载本次故障实验的部分 API；持续请求、Node 状态、事件和重新调度记录齐全 |
| 架构图专业、问题分析深入、总结独到 | 已生成架构图和实际问题分析 | 图中标明入口、组件、服务发现、配置和存储边界；问题分析对应真实日志、假设、验证和修复结果 |
| 可复现的 Git 仓库或 README | 已纳入源码、README 与复现记录 | 现有仓库、合理阶段提交、版本锁定、完整 README、验证脚本和从全新 clone 开始的实际复现记录 |

PDB 验证使用 Kubernetes eviction/drain 路径观察其作用；直接删除 Pod 的基础自愈实验单独执行。PDB 不阻止直接删除，也不保护节点突然失联。

节点故障实验需事先检查 Pod 分布。入口、单实例 Redis 及其本地 PV 保留在存活节点，本次停止仅承载部分 API 的 worker。记录检测和调度的实际超时、错误请求及恢复过程。单机 Kind 只能证明模拟节点故障下的应用行为；同一宿主机、单控制面、单实例 Redis 的故障边界要写清。

优先组合为可复现 Git/README、StatefulSet/PDB、三节点中的 API 故障实验，以及规范架构图和真实问题分析。HPA 可加强伸缩展示，但文档没有将它单独列为加分项。
